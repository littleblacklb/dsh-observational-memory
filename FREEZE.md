# The two lines

This repository is the **standalone plugin line**: two packages that install into
any DeepSeek Harness from npm, with no change to the harness repository itself.

The earlier line — memory stored in the session log with a Memory tab in the web
client — is frozen, not deleted. It required editing the harness repository, so it
could never be distributed. It is preserved here, on branch `parked/browser-ui`,
and nowhere else: the harness checkout that used to carry both halves has been
cleaned of them.

The two lines share everything except the storage layer:

| | Frozen line | This line |
|---|---|---|
| Ledger lives in | the session log (`memory/*` events + a projection) | a per-session store this plugin owns |
| Browser surface | Memory tab + composer-dock reading | none |
| Harness repository | modified | untouched |
| Distributable | no | yes |

## Why the frozen line could not ship

Three session event types (`memory/observations-recorded`,
`memory/reflections-recorded`, `memory/observations-dropped`) have to be compiled
into the harness: `KNOWN_SESSION_EVENT_TYPES` is generated by scanning that
repository, and the persistence read path refuses to interpret a log containing an
event type it does not know and that is not marked `ignorable`. `Session.append`
offers no path to set that marker, and these events must not carry it anyway —
they decide whether compaction renders from memory or falls back to the model.

So a session written with memory in the log is readable only by the fork that
declares the types. Running the packages standalone reproduces this exactly:

```
SessionFormatUnsupportedError: session "memory-roundtrip" contains event type
"memory/observations-recorded" (seq 0) unknown to this harness and not marked
ignorable; refusing to interpret the log — it was likely written by a newer harness
```

Upstream has pull requests disabled (`has_pull_requests: false`), so the types
cannot be contributed either.

## What this line gives up

- Memory is not reconstructable from the session log alone: copying a session
  elsewhere does not carry its memory.
- A fork does not inherit the parent's memory, because the child gets a new
  session id.
- No memory surface in the web client. Status is read through `/om` and the
  `memory_recall` tool, both of which are public plugin seams.
